## 第一個可驗收切片：背景快速回應

用一個工作對話、一個單選問題與一張成果卡串起流程。先使用可控制的測試資料驗證平台與錯誤狀態，再接既有 gateway。測試資料通過不代表真實推播或 API 整合通過。

| 流程 | 通過條件 |
|---|---|
| 權限 | 分別處理通知權限與顯示在其他 App 上層的權限；拒絕浮窗時仍可由通知進入對話；兩者皆拒絕時保留 App 內待處理入口 |
| App 切到背景 | 在另一個 App 上方顯示真正的 Android 浮窗，可關閉並回到原 App；記錄啟動來源與 Android 版本 |
| 重新查詢 | 浮窗先顯示確認中，取得最新問題狀態前不可回答；通知內的舊資料不可直接當作有效問題 |
| 確認與提交 | 使用者選答案後明確按送出；重新檢查有效性與控制權；送出中避免重複點擊 |
| 過期／其他裝置已處理 | 移除回答動作；處理者與時間只在後端確實提供時顯示 |
| 控制權在其他裝置 | 顯示目前控制來源，不自動強制接管；讓使用者明確決定是否取得控制權 |
| 離線／結果不明 | 保留選擇；離線不可送出；送出後斷線顯示結果不明，只能查詢結果，不自動重送 |
| 回到完整對話 | 開啟同一個 session，顯示最新問題狀態；保留對話草稿，關閉浮窗不等於回答 |
| 生命週期 | 分別測試一般背景、程序被系統回收、鎖定螢幕、旋轉／分割視窗；不可用一般背景通過代表其他情境通過 |

必須區分兩種啟動來源：**使用者點通知後開浮窗**與**背景推播到達後自動開浮窗**。兩者分開驗證、分開記錄，不把前者的成功視為後者可用。Android 15 起，以浮窗權限豁免背景啟動前景服務時，還要求已有可見浮窗；單純取得權限不足以保證任意背景啟動。無法自動顯示的狀態需走通知入口。[Android 官方限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

Flutter 與 Android 原生層可透過 platform channel 銜接。浮窗需在哪一層繪製、是否使用獨立 Flutter engine，應依背景生命週期驗證結果決定。[Flutter 官方文件](https://docs.flutter.dev/platform-integration/platform-channels)

## 同一切片的版型與成果檢查

- 手機窄版及鍵盤出現時，確認與送出仍可觸及；使用實際系統 insets。
- 平板依 600／840 寬度門檻切換；開右欄時收起側欄，縮放不丟草稿、session 與已開成果。
- 成果正在閱讀 v1 時到達 v2，只顯示提示；按切換才顯示 v2。回到 v1 可還原原閱讀位置。
- 關鍵按鈕的可點區域至少 48 logical pixels，可大於可見圖示。
